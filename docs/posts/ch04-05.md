# [MLOps] CH4·5 — MLflow·Feast·KFP 연결 실습과 기존 k3s 비교

GitHub에 적어둔 k3s 인프라 비교에 CH4·5의 개념과 실제 연결 실습을 추가했다. 기존 숫자 분류 코드를 유지하면서 실험 추적, 모델 등록, 피처 조회, 배치 추론을 붙였다.

먼저 챕터 이름을 구분했다. 별도로 받았던 Kubernetes 자료의 CH4·5는 자동 운영과 자원 관리였다. 이 글의 챕터는 MLOps 책 기준이며 CH4는 MLflow·Feast, CH5는 Kubeflow Pipelines이다. Kubernetes 비교는 뒤에 보충으로 넣었다.

## CH4. 실험과 모델을 기록하는 MLflow

이전에는 `metrics.json`과 `model.pt`를 저장했다. 실행이 늘어나면 어느 설정으로 학습했고 어떤 데이터와 모델이 연결되는지 직접 찾아야 한다. MLflow는 이런 실행 기록을 모아 비교하는 도구로 이해했다.

| 구분 | 내가 이해한 역할 | 이번 실습에서 연결한 내용 |
|---|---|---|
| Experiment | 관련 실험 실행을 묶는 단위다 | `digits-ch04-ch05` 실험을 만들었다 |
| Run | 한 번 실행한 학습의 기록이다 | seed, epochs, batch size, device와 평가 지표를 남겼다 |
| Artifact | 실행 결과로 남긴 파일이다 | 모델과 지표 파일을 저장했다 |
| Model Registry | 이름과 버전으로 모델을 관리한다 | `digits-mlp-ch45`를 등록하고 버전 URI로 다시 읽었다 |

(보충: 모델을 레지스트리에 등록했다고 곧바로 추론 서비스에 배포되는 것은 아니다. 등록, 운영 모델 선택, 서비스 배포는 구분해야 한다.)

이번에는 기존 검증 정확도 기준을 통과한 모델만 등록했다. 데이터·분할·학습 코드 해시도 기록했고 등록된 모델을 재로딩한 뒤 저장 전 모델의 출력과 비교했다. MLflow는 실행별 SQLite DB와 파일 저장소를 사용했다. 여러 사용자가 접속하는 공유 MLflow HTTP 서버를 배포한 구성은 아니다.

## CH4. 모델 입력을 관리하는 Feast

Feast는 모델에 넣는 피처를 정의하고 학습이나 추론에서 조회하는 도구로 이해했다. 모델 가중치를 저장하는 MLflow Registry와 역할이 다르다.

이번에는 digits 이미지의 64개 픽셀을 0~1 범위로 정규화해 피처로 사용했다. 작은 이미지 예제라 피처 스토어가 꼭 필요한 규모는 아니지만 기존 예제의 입력을 유지하면서 조회 흐름을 연습했다.

| 개념 | 이번 예제로 이해한 내용 |
|---|---|
| Entity | 피처를 찾을 대상이다. 이미지의 `sample_id`를 키로 사용했다 |
| FeatureView | 피처 이름·타입·데이터 출처 등을 묶어 정의한다. `pixel_0`부터 `pixel_63`까지 정의했다 |
| Offline store | 과거 시점 기준 피처 조회에 사용한다. 이번에는 Parquet 파일을 사용했다 |
| Online store | 빠른 조회를 위해 엔티티별 최신 피처를 보관한다. 이번에는 SQLite를 사용했다 |
| Materialization | 원본 피처를 online store에 적재하는 과정이다 |

### 미래 데이터를 섞지 않는지 확인했다

학습 시점에는 알 수 없던 미래 값을 가져오면 평가가 실제보다 좋게 나올 수 있다. 그래서 피처의 시점을 맞춰 조회하는 과정도 검사했다.

첫 번째 샘플에 값이 다른 미래 버전을 하나 추가한 뒤 그보다 앞선 시점으로 조회했더니 원래 값이 반환됐다. Online store에 넣은 테스트 샘플 360개의 값도 원본을 정규화한 값과 대조했다.

(보충: digits에는 실제 이벤트 시각이 없으므로 날짜는 검증용으로 만든 값이다. 실제 운영 데이터의 시간 품질을 검증했다는 뜻은 아니다.)

피처가 64개인지, 누락되거나 null인 값이 없는지, 정규화 범위를 벗어나지 않는지도 검사했다. 조회 결과의 행 순서가 달라져도 요청한 `sample_id` 순서로 맞춰 모델에 넣도록 했다.

## CH5. 배치 추론을 KFP로 연결했다

CH5 원문은 CH4의 소득 분류 모델과 피처를 이용하는 배치 추론 흐름이었다. 나는 기존 GitHub의 digits 예제를 유지해서 아래 네 단계로 연결했다.

```text
read-data
   ↓ 요청할 sample ID와 조회 시점
retrieve-features
   ↓ Feast에서 조회한 64개 피처
run-inference
   ↓ MLflow 모델 버전으로 계산한 예측
write-data
   ↓ batch-predictions.json
```

각 단계의 출력을 다음 단계 입력으로 연결해 의존 관계를 표현했다. 이 DAG를 KFP Python DSL로 정의하고 `pipeline.yaml`로 컴파일했다. 파일 생성에서 끝내지 않고 네 컴포넌트도 실제 실행했다.

### 이번 실행 방식은 구분해서 적었다

KFP의 `SubprocessRunner`를 사용해 로컬 CPU에서 먼저 확인한 뒤 k3s에서는 e101의 단일 GPU Job 안에서 같은 흐름을 실행했다. 모델 학습은 CUDA를 사용하고 배치 추론은 CPU에서 실행한다.

컴포넌트마다 별도 Pod가 생기는 KFP 서버 실행과는 다르다. KFP 서버·UI, 원격 오브젝트 저장소, 캐시·재시도 정책까지 검증한 것은 아니다. 지금 생성한 YAML을 그대로 KFP 서버에 올리려면 코드가 포함된 이미지와 경로·저장소 구성을 추가로 맞춰야 한다. [KFP 로컬 실행 문서](https://www.kubeflow.org/docs/components/pipelines/user-guides/core-functions/execute-kfp-pipelines-locally/)에서도 로컬 실행의 범위를 따로 설명하고 있다.

## 보충. 사전 준비를 기존 k3s 인프라로 대체했다

이미 인프라를 구축해서 사용하고 있으므로 kind로 새 클러스터를 만드는 과정은 반복하지 않았다. GitHub에 적어둔 비교에서 이번 실습과 관련 있는 항목을 가져왔다. 아래 기존 인프라 상태는 2026-10-30에 조회한 내용이다.

| 학습 자료에서 다룬 항목 | 기존 인프라와 비교한 내용 |
|---|---|
| Kubernetes 클러스터 준비 | 기존 k3s 9개 노드가 Ready였다. 새 클러스터 설치 대신 이 환경에서 실습했다 |
| GPU 실행 환경 | e101은 RTX 4070 Ti, e102는 RTX 4070이며 GPU 자원을 각각 1개 노출했다. 이번 실행은 e101만 사용했다 |
| 결과 보관 | 기존 Ceph RBD를 사용했다. 새 연결 실습 결과는 별도 5Gi PVC에 저장하도록 했다 |
| Metrics API | metrics-server 2/2 Ready, Metrics API Available, 9개 노드의 `kubectl top` 조회를 확인했다 |
| 지속 관측 | VictoriaMetrics·Grafana·DCGM Exporter가 있었다. 이번 모델의 품질 지표와 경보까지 연결한 상태는 아니다 |
| readiness·liveness | 기존 metrics-server와 Grafana에서 설정을 확인했다. 조회한 두 Deployment에는 startupProbe가 없었다 |
| 배포 전략 | metrics-server는 RollingUpdate, Grafana는 Recreate였다. 이번 학습은 완료되는 Job이므로 추론 서비스의 무중단 배포 실습과 구분했다 |
| requests·limits | 이번 Job은 CPU 500m/2, 메모리 2Gi/6Gi, GPU 1/1로 지정했다. 부하 시험으로 최적값을 산정한 결과는 아니다 |

(보충: CPU·메모리 request와 limit이 다른 이번 Job 구성은 Burstable에 해당한다. GPU request와 limit이 같다는 사실만으로 Guaranteed가 되지는 않는다.)

기존 모니터링, GPU 자원 노출, 저장소는 재사용했다. MLflow Registry나 Feast 피처 정의처럼 모델과 데이터에 가까운 부분은 실습 코드에서 새로 연결했다. 인프라가 있다는 사실만으로 MLOps 도구들의 연동까지 완료된 것은 아니라고 정리했다.

## 실제 실행 결과

2026-10-30에 로컬 CPU 검증을 거친 뒤 e101 GPU Job으로 실행했다.

| 확인 항목 | 결과 |
|---|---|
| 학습 장치 | e101 RTX 4070 Ti, CUDA 12.6, PyTorch 2.8.0+cu126 |
| 검증·테스트 정확도 | 95.54% / 96.67% |
| MLflow | `digits-mlp-ch45` 버전 1 등록 및 재로딩 비교 통과 |
| Feast | 미래 값 제외 검사, 테스트 360개 온라인 피처 값 비교 통과 |
| KFP | read-data → retrieve-features → run-inference → write-data 모두 SUCCESS |
| 배치 결과 | 테스트 360개 중 348개 정답, 학습 코드의 테스트 정확도와 일치 |
| Kubernetes | Job Complete 1/1, Pod Succeeded, 종료 코드 0 |
| 실행 시간 | Job 전체 116초. 이미지 준비와 패키지 설치를 포함한 값이다 |
| 코드 검사 | 기존 학습 테스트와 피처 계약 테스트를 합쳐 14개 통과 |

(보충: 배치 추론은 기존 테스트 세트를 다시 사용한 연결 검증이다. 새로운 데이터로 일반화 성능을 추가 평가한 결과는 아니다. 이번에는 e102를 사용하지 않았다.)

실행 중 MLflow 3.16의 기본 PyTorch 저장 형식이 `pt2`로 바뀐 부분과 Feast Entity의 타입 지정에서 오류가 있었다. 설치된 API를 확인해 저장 형식과 `ValueType.INT64`를 명시했고 CPU에서 전체 흐름이 통과한 다음 e101에 실행했다. 모델은 이번 실행에서 직접 만든 파일만 재로딩했다.

기존에는 모델 파일이 저장됐는지 확인하는 데서 끝났다면 이번에는 모델 버전으로 다시 읽고 피처를 조회해 배치 결과를 남기는 과정까지 연결했다. 다음에는 공유 MLflow 서버와 원격 저장소를 연결하고 KFP 서버에서 컴포넌트를 별도 Pod로 실행하는 부분을 확인할 차례다.
